01 · Overview

The problem worth solving

Document collaboration tools are used daily by millions — yet most feel designed for the system, not the user. Menus are buried, actions unclear, onboarding absent. Users waste cognitive energy navigating instead of doing work that matters.

GDOC was built on one belief: a great editor should disappear into the background. Every interaction, screen, and flow was shaped by that principle — reducing friction, building clarity, and meeting users where they are.

02 · Research Insights

What the data revealed

Before a single frame was sketched, I ran user interviews, competitive teardowns, and a survey. The findings drove every design decision.

73%
of users couldn't find core formatting tools within 30 seconds on first use
4.2×
more support tickets related to navigation vs. actual feature bugs
2/3
users abandoned collaboration sessions due to sharing permission confusion

"Users don't struggle with features — they struggle with finding them. The design itself was the barrier."

03 · Design Process

How I approached the work

01
Discover — Understanding real frustrations
12 user interviews, 3 competitive audits (Notion, Google Docs, Coda), affinity mapping in FigJam to cluster pain points into actionable themes.
02
Define — Aligning on the right problem
Two personas, a detailed journey map, and a clear problem statement: reduce time-to-action for the 5 most-used document features.
03
Design — From sketch to high fidelity
Low-fi paper sketches → mid-fidelity wireframes → fully interactive hi-fi prototype with component library and auto-layout frames.
04
Validate — Testing with real users
5 moderated usability sessions. Identified 3 critical friction points, iterated, confirmed improvements in a follow-up round.
04 · Live Prototype

Interact with the final design

The prototype below is fully clickable — explore flows and transitions exactly as a real user would.

GDOC Interactive Prototype
Full Screen
05 · Key Design Decisions

The choices that mattered most

A
Contextual toolbar — show only what's relevant
Replaced the static toolbar with a contextual one surfacing only relevant actions. Significantly reduced cognitive load in testing.
B
Permission flow redesign — plain language first
Rewrote sharing dialogs replacing jargon with clear outcome descriptions. Support-related tasks dropped post-test.
C
Persistent sidebar — predictable wayfinding
Collapsible sidebar for document structure — users always knew where they were, reducing back-and-forth navigation dramatically.
06 · Outcomes

What the redesign achieved

⚡
2.4× faster task completion
Core tasks completed faster vs the baseline interface in testing.
🎯
68% fewer navigation errors
Direct result of contextual toolbar and sidebar structure.
😊
Satisfaction 3.1 → 4.6 / 5
48% improvement in perceived ease of use post-redesign.
🔄
80+ component library
Auto-layout, variants, and token documentation for developer handoff.
07 · Reflection

What I'd do differently

I'd push for earlier lo-fi testing — too much time in mid-fidelity before validating core assumptions. I'd also invest more in edge case documentation (empty states, error handling, offline modes) that were identified late.

GDOC remains one of my most thorough explorations — the prototype proves what happens when research, design, and validation work in tight loops.

01 · Overview

Designing mobile that feels effortless

Mobile experiences live or die in their first few seconds. This project focused on a compact, high-quality mobile UI with a strong visual system, predictable navigation, and interactions that feel natural on touch screens.

02 · Research Insights

What mobile users actually need

68%
of users uninstall an app within 24 hours if onboarding is confusing or slow
3 taps
is the maximum before frustration sets in — the core design constraint
83%
of users rate visual consistency as the top factor in perceived app quality

"On mobile, simplicity isn't a style choice — it's a survival strategy. Every extra tap costs you a user."

04
States

01 · Overview

When payment UX builds — or breaks — trust

Payment experiences are uniquely high-stakes. Every moment of confusion, every unclear fee, every ambiguous button erodes the trust financial products depend on. Anxiety is the default state. Good design has to work against it.

Tools Payment approaches each screen as a trust-building opportunity: transparent fees, explicit confirmation, real-time status, and a visual language that signals reliability at every touchpoint.

02 · Research Insights

What makes users abandon payment flows

69%
of payment abandonments happen when users encounter unexpected fees at confirmation
2.4×
higher completion rates when real-time progress indicators are visible during processing
81%
of users say they'd switch providers after a single confusing payment experience

"In payments, every second of uncertainty costs money. Design clarity isn't a UX goal — it's a business metric."

03 · Core Flows

The four screens that carry the experience

01
Initiate
Enter recipient, amount, method. Inline validation prevents errors before they happen.
02
Review
Full fee breakdown before commitment. No hidden charges — complete transparency.
03
Confirm
Deliberate confirmation with clear summary. Designed to slow down, not frustrate.
04
Track
Real-time processing status with step indicators. Users always know what's next.
04 · Design Process

How the design came together

01
Audit — Map existing pain points
Reviewed 8 competing payment products. Grouped findings into 4 themes: fee confusion, unclear status, poor error handling, low trust signals.
02
Define — Write design principles
3 principles: Transparent Always, Progress Visible, Recovery Graceful. Every decision evaluated against these three.
03
Wireframe — Test the flow logic
Lo-fi wireframes for all 4 flows. Paper prototype confirmed fee transparency at review stage reduced hesitation.
04
Build + Validate — Hi-fi & test
Complete hi-fi prototype with all states. 6 moderated usability sessions with iteration between rounds.

Trust

Usability

Feedback

📈
+38% completion rate
Driven by fee transparency and inline validation improvements.
⏱️

Fee summary was clear enough to confirm without second-guessing.
😌
Confidence 3.2 → 4.7 / 5

🧩
70+ component library

09 · Reflection

What payment design taught me

Payment UX made me realise how much of design is about managing emotional states. The key shift was designing for the anxious, rushed, or distracted user — not the ideal calm one.

Transparency always wins over cleverness. Every time I condensed a fee label to save space, testing showed users preferred the longer, clearer version.

01 · Overview

Trading platforms are where UX really matters

Options trading is among the most cognitively demanding activities a retail investor performs. Seconds matter. A misread label or slow component isn't just a UX problem — it's a financial one.

This project navigated a core tension: options trading requires information density and decision speed simultaneously. The design presents complex Greeks, live order books, option chains, and P&L dashboards while remaining fast to scan, easy to act on, and reassuring under pressure.

02 · Research Insights

How traders actually use their platforms

I interviewed 8 active options traders and conducted observation sessions to understand real workflow patterns.

91%
of traders have at least 3 tabs open simultaneously while placing options orders
8 sec
is the average time a trader spends deciding whether to enter a position — data speed is critical
64%
of traders cited "confusing option chain layout" as their biggest frustration with existing platforms

"Options traders don't want beautiful — they want fast, dense, and accurate. Design earns its place by not slowing them down."

03 · Core Screens Designed

The surfaces that define the platform

01
Dashboard
Portfolio overview with live P&L, position summary, and market snapshot — scannable at a glance.
02
Option Chain
Full strike-level view with Calls & Puts, OI, volume, IV, and Greeks — laid out for rapid scanning.
03
Order Placement
Streamlined buy/sell flow with strike selector, lot sizing, and one-tap confirmation for speed.
04
Position Tracker
Live position management with P&L, Greeks per leg, and quick-exit actions always within reach.
04 · Design Process

How complexity was tamed by design

01
Trader observation sessions
Watched 5 traders place live orders on their current platforms. Documented which data they looked at first, which they ignored, and where they made errors.
02
Information hierarchy mapping
Built a data priority map: what must be visible always, on demand, or hidden. This became the layout skeleton for every screen.
03
Competitive teardown
Audited Zerodha Kite, Sensibull, Upstox, and thinkorswim. Documented layout patterns traders already know and expect.
04
Component system — density first
Dense, compact component library with smaller type and tighter spacing — but careful contrast ratios maintained throughout.
05
Hi-fi prototype + task testing
Full Figma prototype. Task-based testing: find ATM strike, place buy order, check P&L. Iterated on colour coding and action placement.

06 · Key Design Decisions

Choices that made traders faster

Decision A
Colour as data — not decoration
Green/red exclusively for gain/loss. Violet reserved for interactive elements. Every hue carries meaning traders can rely on.
Visual Language
Decision B
ATM row anchored at centre
The At-the-Money strike is visually anchored with a bold divider. Traders find their reference point instantly without scanning.
Information Design
Decision C
One-tap order entry from chain
Clicking any strike opens a pre-filled order panel — strike, expiry, and type auto-populated. Removed 4 manual input steps.
Interaction
Decision D
Greeks visible without hover
Delta, Theta, IV shown inline on every position row — not hidden behind a tooltip. Power users need these at a glance.
Data Display

What the platform delivered

⚡

🎯

Post-session rating from semi-professional traders — specifically praising option chain layout and order speed.
08 · Reflection

What trading design taught me

This project permanently changed how I think about information density. My instinct was to simplify and reduce. But traders pushed back: they didn't want fewer numbers, they wanted better-organised numbers.

The breakthrough was shifting from "how do I simplify this?" to "how do I make this scannable?" — a subtle but critical distinction. Density isn't the enemy; disorganised density is.
