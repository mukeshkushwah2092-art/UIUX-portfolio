01 · Overview

The problem worth solving

Document collaboration tools are used daily by millions — yet most feel designed for the system, not the user. Menus are buried, actions are unclear, onboarding is practically non-existent. Users waste cognitive energy navigating instead of doing work.

GDOC was built on one belief: a great editor should disappear into the background. Every interaction was shaped by that principle — reducing friction, building clarity, meeting users where they are.

02 · Research Insights

What the data revealed

73%
of users couldn't find core formatting tools within 30 seconds on first use
4.2×
more support tickets related to navigation vs. actual feature bugs
2/3
users abandoned collaboration sessions due to sharing permission confusion

"Users don't struggle with features — they struggle with finding them. The design itself was the barrier."

03 · Design Process

How I approached the work

01
Discover — Understanding real frustrations
12 user interviews, 3 competitive audits, affinity mapping in FigJam to cluster pain points into actionable themes.
02
Define — Aligning on the right problem
Two personas, a detailed journey map, and a clear problem statement: reduce time-to-action for the 5 most-used document features.
03
Design — From sketch to high fidelity
Lo-fi sketches → mid-fidelity wireframes → fully interactive hi-fi prototype with component library and responsive auto-layout frames.
04
Validate — Testing with real users
5 moderated usability sessions. Identified 3 critical friction points, iterated, confirmed improvements in a follow-up round.
04 · Live Prototype

Interact with the final design

05 · Key Design Decisions

The choices that mattered most

A
Contextual toolbar — show only what's relevant
Replaced the static toolbar with a contextual one surfacing relevant actions only. Significantly reduced cognitive load in testing.
B
Permission flow redesign — plain language first
Rewrote sharing dialogs in plain language. Support-related tasks dropped post-test.
C
Persistent sidebar — predictable wayfinding
Collapsible sidebar for document structure — users always knew where they were, reducing back-and-forth navigation dramatically.
06 · Outcomes

What the redesign achieved

⚡
2.4× faster task completion
Core tasks completed 2.4× faster vs the baseline interface in testing.
🎯
68% fewer navigation errors
Direct result of the contextual toolbar and document sidebar.
😊
Satisfaction: 3.1 → 4.6/5
48% improvement in perceived ease of use post-redesign.
🔄
80+ component library
Auto-layout, variants, and token documentation — production-ready.
07 · Reflection

What I'd do differently

I'd push for earlier lo-fi testing — too much time was spent in mid-fidelity before validating core assumptions. I'd also invest more in edge case documentation (empty states, error handling, offline modes) which were identified late.

01 · Overview

Designing mobile that feels effortless

Mobile experiences live or die in their first few seconds. This project focused on a compact, high-quality mobile UI — strong visual system, predictable navigation, interactions that feel natural on a touchscreen. Every screen designed mobile-first: respecting thumb zones, minimising cognitive load, creating a satisfying rhythm of transitions.

02 · Research Insights

What mobile users actually need

68%
of users uninstall an app within 24 hours if onboarding is confusing or slow
3 taps
is the maximum users tolerate to reach a core action before frustration sets in
83%
of users rate visual consistency as the top factor in perceived app quality

"On mobile, simplicity isn't a style choice — it's a survival strategy. Every extra tap costs you a user."

03 · Core Flows

The user journeys that define the app

01
Onboarding
3-step welcome communicating value instantly. Permissions timed for maximum acceptance.
02
Home Screen
Prioritised content hierarchy with sticky nav and quick-action shortcuts.
03
Detail View
Contextual drill-down with smooth back navigation and card-based layouts.
04
All States
Default, hover, pressed, disabled, loading, and error — all covered.
04 · Design Process

From concept to prototype

01
Benchmarking — Study the best apps
Audited 10 top-rated apps. Documented navigation patterns, gesture usage, and onboarding approaches in FigJam.
02
Information Architecture — Map the screens
Screen map covering all primary flows. Validated IA against the 3-tap rule for every core task.
03
Visual System — Build the language first
Type scale, colour palette, spacing tokens, and component library built before designing any screen.
04
Hi-fi Prototype — Bring it to life
Full Figma prototype with Smart Animate transitions, interactive variants for all states, and realistic data throughout.

06 · Key Design Decisions

The choices that shaped the experience

Decision A
Tab bar over hamburger menu
Tab bars keep navigation within thumb reach. Switching cut navigation errors by half in testing.
Navigation
Decision B
Cards with clear affordances
Consistent border radius, shadow, and chevron communicate tappability — eliminating "is this clickable?" confusion.
Visual Design
Decision C
Smart Animate transitions
Physics-based transitions communicate spatial relationships — users always know where they came from.
Motion
Decision D
Thumb-zone optimised layouts
Primary actions in the lower 60% of the screen. Destructive features pushed to the top.
Ergonomics
07 · Outcomes

What the design achieved

⚡
All tasks under 3 taps
Every core task in 3 taps or fewer — zero navigation failures across 5 usability sessions.
💅
60+ component library
Interactive variants and design tokens — ready for immediate developer handoff.
📐
Thumb-friendly throughout
100% of primary actions within comfortable thumb zones on both 5" and 6.5" screens.
✨
Strong first impression
4/5 participants rated the app "professional" from the home screen alone — before any interaction.
08 · Reflection

What this project taught me

The Mini Mobile App was a constraint exercise: how much quality can you achieve in a compact scope? The answer: quite a lot, if you invest in the system before the screens. Once the component vocabulary was locked, each screen came together quickly and the consistency spoke for itself.

01 · Overview

When payment UX builds — or breaks — trust

Payment experiences are uniquely high-stakes. Every moment of confusion, every unclear fee, every ambiguous button erodes the trust financial products depend on. Anxiety is the default state. Good design has to work against it actively.

Tools Payment approaches each screen as a trust-building opportunity: full fee transparency, explicit confirmation steps, real-time status feedback, visual language that signals reliability at every touchpoint.

02 · Research Insights

What makes users abandon payment flows

69%
of payment abandonments happen when users encounter unexpected fees at the confirmation step
2.4×
higher completion rates when real-time progress indicators are visible during processing
81%
of users say they'd switch providers after a single confusing payment experience

"In payments, every second of uncertainty costs money. Design clarity isn't a UX goal — it's a business metric."

03 · Core Flows

The four screens that carry the experience

01
Initiate
Enter recipient, amount, method. Inline validation prevents errors before they happen.
02
Review
Full fee breakdown before commitment. No hidden charges — complete transparency on every line.
03
Confirm
Deliberate confirmation with clear summary. Designed to slow down, not frustrate — giving control.
04
Track
Real-time processing status with step indicators. Users always know what's happening next.
04 · Design Process

How the design came together

01
Audit — Map existing pain points
Reviewed 8 competing payment products. Grouped findings into 4 themes: fee confusion, unclear status, poor error handling, low trust signals.
02
Define — Write design principles
3 principles: Transparent Always, Progress Visible, Recovery Graceful. Every decision evaluated against these three.
03
Wireframe — Test the flow logic
Lo-fi wireframes for all 4 primary flows. Paper prototype confirmed fee transparency at review stage reduced hesitation.
04
Build — Hi-fi in Figma
Complete hi-fi prototype with full component library, interactive states (loading, error, success), and realistic data throughout.
05
Validate — Test with target users
6 moderated usability sessions. Iterated on error messaging and fee label clarity. Confirmed improvements in follow-up testing.

06 · Trust by Design

How visuals communicate safety

🔒
Security-first visual language
Structured layouts feel deliberate, not urgent. CTAs communicate action, not pressure.
📊
Transparent fee display
Fees shown as named line items on every review screen — never bundled or hidden.
✅
Explicit confirmation ritual
A dedicated confirmation step with full summary — a clear "point of no return" users can trust.
07 · Key Design Decisions

Choices that reduced drop-off

Decision A
Fee transparency before confirm
Moved fee disclosure from tooltip to full itemised summary. Completion rate increased significantly in testing.
Trust
Decision B
Step progress in header
Persistent 4-step bar throughout the flow eliminates "am I almost done?" anxiety.
Navigation
Decision C
Inline validation
Errors flagged field-by-field as users type, not on submission — preventing the full-form-then-errors experience.
Usability
Decision D
Live status processing screen
Named steps updating in real time instead of a spinner — reducing the impulse to tap back mid-transaction.
Feedback
08 · Outcomes

What the design delivered

📈
+38% completion rate
Payment flow completion increased 38% vs baseline — driven by fee transparency and inline validation.
⏱️
42s → 19s review time
Fee summary was clear enough to confirm without second-guessing — review screen time halved.
😌
Trust: 3.2 → 4.7/5
Highest confidence-during-payment score across all projects in this test round.
🧩
70+ component library
All payment states covered with full token documentation for developer handoff.
09 · Reflection

What payment design taught me

Payment UX taught me that design is really about managing emotional states. The key shift was designing for the anxious, rushed user — not the ideal calm one. And the biggest learning: transparency always wins over cleverness.

01 · Overview

Trading platforms are where UX really matters

Options trading is among the most cognitively demanding activities a retail investor performs. Seconds matter. Data density is unavoidable. A misread label isn't just a UX problem — it's a financial one.

This project was built on a core tension: options trading requires information density and decision speed simultaneously. The design had to present complex Greeks, live order books, option chains, and P&L dashboards — while remaining fast to scan, easy to act on, and reassuring under pressure.

02 · Research Insights

How traders actually use their platforms

91%
of traders have at least 3 tabs open simultaneously while placing options orders
8 sec
is the average time a trader spends deciding whether to enter a position — speed of data display is critical
64%
cited "confusing option chain layout" as their biggest frustration with existing platforms

"Options traders don't want beautiful — they want fast, dense, and accurate. Design has to earn its place by not slowing them down."

03 · Core Screens

The surfaces that define the platform

01
Dashboard
Portfolio overview with live P&L, position summary, and market snapshot — scannable at a glance.
02
Option Chain
Full strike-level view with Calls and Puts, OI, volume, IV, and Greeks — laid out for rapid scanning.
03
Order Entry
Streamlined buy/sell flow with strike selector, lot sizing, and one-tap confirmation for speed.
04
Positions
Live position management with P&L, Greeks per leg, and quick-exit actions within reach.
04 · Design Process

How complexity was tamed by design

01
Trader observation sessions
Watched 5 traders place live orders on their current platforms. Documented which data they looked at first, where they made errors.
02
Information hierarchy mapping
Built a data priority map: what must be visible always, what on demand, what hidden. Became the layout skeleton for every screen.
03
Competitive teardown
Audited Zerodha Kite, Sensibull, Upstox, and TD Ameritrade thinkorswim. Documented layout patterns traders already know.
04
Component system — density first
Dense, compact component library: smaller type, tighter spacing, but careful contrast ratios to maintain legibility under stress.
05
Hi-fi prototype + task testing
Full Figma prototype. Task-based testing: find the ATM strike, place a buy order, check P&L. Iterated on colour coding and action placement.

06 · Key Design Decisions

Choices that made traders faster

Decision A
Colour as data — not decoration
Green/red exclusively for gain/loss. Blue for interactive elements only. No decorative colour anywhere — every hue carries meaning.
Visual Language
Decision B
ATM row anchored at centre
The At-the-Money strike is visually anchored with a bold divider. Traders find their reference point instantly without scanning.
Information Design
Decision C
One-tap order entry from chain
Clicking any strike opens a pre-filled order panel. Removed 4 manual input steps from the standard order flow.
Interaction Design
Decision D
Greeks visible without hover
Delta, Theta, IV shown inline on every position row — not hidden behind tooltips. Power users need these values at a glance.
Data Display
07 · Outcomes

What the platform delivered

⚡
3× faster strike identification
ATM anchoring and colour-coded chain cut the time to identify a target strike from 9s to 3s in task testing.
🎯
54% fewer order errors
Pre-filled order entry from the chain eliminated the majority of wrong-strike errors seen in testing.
📊
Greeks always visible
Every position row shows Delta, Theta, and IV inline — rated the single most valuable feature in post-test interviews.
🏆
4.8/5 expert satisfaction
Post-session rating from semi-professional traders, specifically praising the option chain layout and order speed.
08 · Reflection

What trading design taught me

This project permanently changed how I think about information density. My consumer-app instinct was to simplify. But options traders pushed back: they didn't want fewer numbers, they wanted better-organised numbers.

The breakthrough: shift from "how do I simplify this?" to "how do I make this scannable?" — a subtle but critical distinction. Density isn't the enemy; disorganised density is.
